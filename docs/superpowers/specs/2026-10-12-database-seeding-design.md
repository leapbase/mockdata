# Direct database seeding design

## Goal

Let a developer put generated test rows into an existing empty SQLite, PostgreSQL, or MySQL/MariaDB database without hand-importing files. Keep the existing `generate` and `infer` commands unchanged. A preview is the default; database writes require `--apply`.

## Command contract

```
mockdata seed schema.yaml --target env:TEST_DATABASE_URL
mockdata seed schema.yaml --target env:TEST_DATABASE_URL --apply
mockdata seed schema.yaml --target sqlite:./test.db --seed 42 --apply
```

- `--target` is required. PostgreSQL/MySQL URLs are accepted only through `env:NAME`, resolved from the process environment or the CLI's `.env` loader. SQLite accepts `sqlite:<path>` or a `.db`/`.sqlite`/`.sqlite3` file path. Raw network connection URLs are rejected so passwords do not enter shell history.
- Optional `--seed` overrides the schema seed; `--pg-schema` selects the PostgreSQL schema (default `public`). `--apply` is the only write switch. Invalid or repeated/conflicting arguments fail before opening a database.
- The default command is a dry run. It connects read-only, checks the target, generates and validates the full dataset, then prints the database kind, table insertion order, row counts, seed, and any LLM call/token usage. It does not print connection strings or generated values and performs no writes.
- `--apply` repeats preflight and generation in that invocation, opens a transaction, rechecks that target tables are empty, inserts rows in dependency order, and commits. Any insertion error rolls back and returns a nonzero exit code. It prints committed row counts only after commit.
- A separate dry run is advisory. The `--apply` invocation does its own checks; it never trusts an earlier preview.

## Compatibility and write rules

The seeder inspects raw catalog names and constraints rather than relying on sanitized names from `infer`. Every generated table must have exactly the same column names as its target table; other database tables may exist but are not touched. Reject schema/target mismatches, unsupported mapped types, composite primary/foreign/unique keys that the generator cannot model, and foreign keys that depend on a table outside the selected schema. Report the first useful reason before any write. Database-side CHECK constraints and triggers can still reject an insert; that rejection rolls back the transaction.

All target tables in the generated schema must be empty. The command never truncates, updates, or deletes existing rows. Primary keys are generated by the schema as usual, so the first version does not attempt to offset keys or merge with existing data. For MySQL/MariaDB, require transactional tables (InnoDB) before `--apply`; never disable foreign key checks.

Use `planGeneration` for insertion order. Reject plans with deferred foreign keys from table cycles: the generator can fill those in memory, but plain inserts cannot establish that cycle portably across these three databases. Nullable self references can be inserted in row order because they refer only to earlier rows.

SQL identifiers come only from checked catalog names and are quoted for the relevant dialect; values are always parameters. PostgreSQL inserts use the chosen schema, MySQL/MariaDB use the database named by the URL, and SQLite enables foreign key enforcement. The write path must never echo credentials, including in driver errors.

## Components and data flow

1. `packages/cli` adds `seed` parsing and human-readable dry-run/apply reports. It reuses `loadSchemaFile`, `loadEnv`, schema validation, and `generateWithLlm`.
2. A database-write module owns dialect adapters for connection, catalog inspection, empty-table checks, transactions, and parameterized inserts. It shares catalog types/introspection and target detection with `@mockdata/inputs`, without changing the read-only `infer` behavior.
3. A shared preflight function compares parsed schema and target catalog, rejects unsupported relationships, and returns a plan of exact target identifiers and table order. Both dry run and apply use the same comparison.
4. Generation happens before opening a write transaction, so LLM latency does not hold database locks. Apply then rechecks compatibility and emptiness inside its transaction before inserting. The target is assumed to be a dedicated database with no concurrent writers; another client writing at the same time may cause a conflict or mixed data, especially on MySQL. A newly added constraint may cause apply to fail and roll back. No success is reported until commit.

LLM columns use the existing provider configuration. A dry run that includes them can consume model credits. LLM text is generated again during a later `--apply`, so only deterministic columns are guaranteed to match between invocations with the same seed. The CLI help and README will say this explicitly.

## Verification

- CLI tests cover dry-run output, no writes, `--apply`, seed override, argument rejection, and credential redaction.
- Real temporary SQLite databases cover FK insertion order, self references, mismatched schemas, nonempty tables, failed-insert rollback, and `PRAGMA foreign_keys` enforcement.
- Adapter tests cover PostgreSQL schema qualification, MySQL identifier quoting, parameters, and rollback. Optional live Postgres/MySQL integration tests run only when dedicated test database URLs are supplied; they must use disposable empty databases.
- Run build and the full repository test suite. Keep the existing infer and generate tests green. No web UI or MCP database-write endpoint is included in this change.
